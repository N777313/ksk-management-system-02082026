# 1. Назначение финансового ядра

Финансовое ядро является самой важной частью всей системы.

Именно оно гарантирует, что в любой момент времени можно точно ответить на вопросы:

### Для жильца

* Сколько я должен?
* Сколько уже оплатил?
* За какие месяцы оплачено?
* Есть ли переплата?
* Как распределился мой последний платеж?
* Почему у меня именно такой долг?

### Для администратора

* Сколько денег реально поступило?
* Сколько всего начислено?
* Какая задолженность по дому?
* Сколько денег находится в кассе?
* Какие средства уже потрачены?
* Можно ли подтвердить каждую финансовую операцию документом?
* Совпадает ли остаток денежных средств с историей операций?

Все расчеты в системе должны быть полностью воспроизводимыми.

Запрещается хранить рассчитанные значения (долг, баланс, переплата) как основные данные. Они должны вычисляться на основании финансовых документов и операций.

---

# 2. Основные финансовые сущности

Система разделяет четыре независимых понятия.

## 2.1 Начисление (Charge)

Начисление — это обязательство жильца оплатить определенную сумму за конкретный расчетный период.

Пример:

```text
Квартира №15

Август 2026

5400 ₸
```

Начисление показывает только долг.

Оно не означает, что деньги уже поступили.

---

## 2.2 Платеж (Payment)

Платеж — это факт получения денежных средств.

Например:

```text
05.08.2026

64800 ₸
```

Платеж не содержит информации, за какие месяцы он произведен.

---

## 2.3 Распределение платежа (Payment Allocation)

Это связь между платежом и начислениями.

Именно распределение определяет:

```text
Платеж

↓

Август

↓

Сентябрь

↓

Октябрь
```

Все финансовые расчеты строятся на основании распределений.

---

## 2.4 Финансовая операция (Transaction)

Любое движение денежных средств.

Например:

```text
Приход

+

5400 ₸
```

или

```text
Расход

-

80000 ₸
```

Баланс дома рассчитывается только по таблице финансовых операций.

---

# 3. Основные бухгалтерские правила

В системе действуют следующие обязательные правила.

### Правило №1

Начисление не является поступлением денег.

---

### Правило №2

Платеж не закрывает начисления автоматически.

Платеж всегда проходит через механизм распределения.

---

### Правило №3

Все распределения должны храниться постоянно.

Нельзя пересчитывать историю задним числом без оформления корректирующей операции.

---

### Правило №4

История операций неизменяема.

Запрещается физическое удаление:

* платежей;
* начислений;
* расходов;
* выплат зарплаты;
* распределений.

Вместо удаления используются:

* отмена;
* сторнирование;
* корректировка.

---

### Правило №5

Каждая финансовая операция должна иметь источник.

Например:

```text
Receipt

↓

Payment

↓

Allocation

↓

Transaction
```

или

```text
Expense

↓

Transaction
```

---

# 4. Алгоритм ежемесячного начисления

Каждого первого числа месяца автоматически создаются начисления.

Алгоритм:

```text
Получить все активные квартиры

↓

Определить действующий тариф

↓

Создать Charge

↓

Статус = unpaid
```

Для каждой квартиры создается только одно начисление за один расчетный период.

Повторное создание начисления за тот же месяц запрещено.

---

# 5. Правила изменения тарифа

Изменение тарифа не изменяет историю.

Например:

До сентября:

```text
5400 ₸
```

С сентября:

```text
6000 ₸
```

История:

| Период   | Сумма |
| -------- | ----- |
| Август   | 5400  |
| Сентябрь | 6000  |

Ранее созданные начисления не пересчитываются автоматически.

---

# 6. Алгоритм приёма платежа

При поступлении оплаты система выполняет одну транзакцию базы данных.

Последовательность:

1. Создать запись `Payment`.
2. Создать приходную запись `Transaction`.
3. Запустить распределение платежа.
4. Создать записи `PaymentAllocation`.
5. Пересчитать статусы затронутых начислений.
6. Сформировать чек.
7. Записать действие в журнал аудита.

Если любой этап завершился ошибкой, вся операция отменяется (`ROLLBACK`).

---

# 7. Алгоритм распределения платежа

Это основной алгоритм системы.

### Правило

Всегда сначала закрываются самые старые непогашенные начисления.

---

### Пример 1. Полное закрытие долга

Начисления:

| Месяц   | Сумма |
| ------- | ----: |
| Январь  |  5400 |
| Февраль |  5400 |
| Март    |  5400 |

Поступил платеж:

```text
16200 ₸
```

Результат:

```text
Январь ✓

Февраль ✓

Март ✓
```

---

### Пример 2. Частичная оплата

Начисления:

| Месяц   | Сумма |
| ------- | ----: |
| Январь  |  5400 |
| Февраль |  5400 |
| Март    |  5400 |

Поступил платеж:

```text
10000 ₸
```

Распределение:

| Период  | Оплачено |
| ------- | -------: |
| Январь  |     5400 |
| Февраль |     4600 |

Статусы:

| Период  | Статус      |
| ------- | ----------- |
| Январь  | Оплачено    |
| Февраль | Частично    |
| Март    | Не оплачено |

---

### Пример 3. Оплата вперёд

Долгов нет.

Поступило:

```text
64800 ₸
```

Система автоматически распределяет оплату на ближайшие 12 начислений.

Жилец сразу видит:

```text
Оплачено до

Июля 2027 года
```

---

# 8. Правила распределения

Распределение выполняется строго по следующим правилам:

1. Сначала полностью закрываются самые старые задолженности.
2. Частичная оплата допускается.
3. Будущие начисления закрываются только после полного погашения прошлых долгов.
4. Одно начисление может быть покрыто несколькими платежами.
5. Один платеж может покрывать множество начислений.

---

# 9. Переплата

Переплата не является отдельным видом платежа.

Она возникает, когда:

* сумма платежей превышает сумму начислений на текущую дату;
* средства уже распределены на будущие начисления.

Пример:

Начислено:

```text
54000 ₸
```

Оплачено:

```text
64800 ₸
```

Переплата:

```text
10800 ₸
```

Жилец видит:

```text
Оплачено вперёд

2 месяца
```

или

```text
Переплата

10800 ₸
```

---

# 10. Определение задолженности

Долг квартиры определяется как:

```text
Сумма начислений

-

Сумма распределений
```

Используются только распределенные суммы.

Факт наличия платежа без распределения не уменьшает долг.

---

# 11. Баланс дома

Баланс рассчитывается только по финансовым операциям.

Формула:

```text
Баланс

=

Доходы

-

Расходы
```

Доходы — все приходные транзакции.

Расходы — все расходные транзакции.

Баланс никогда не редактируется вручную.

---

# 12. Выплата заработной платы

При выплате зарплаты система автоматически:

1. Создает запись `SalaryPayment`.
2. Создает запись `Expense`.
3. Создает расходную `Transaction`.
4. Формирует расходный документ.
5. Записывает действие в журнал аудита.

---

# 13. Учет расходов

Каждый расход обязан содержать:

* категорию;
* сумму;
* дату;
* ответственного;
* подтверждающий документ (если имеется);
* комментарий.

После сохранения расход сразу уменьшает баланс дома.

---

# 14. Отмена платежа

Физическое удаление платежей запрещено.

При ошибке используется операция отмены.

Алгоритм:

1. Создать сторнирующую запись.
2. Отменить все распределения.
3. Пересчитать статусы начислений.
4. Создать обратную финансовую транзакцию.
5. Записать событие в журнал аудита.

Первоначальный платеж сохраняется в истории со статусом «Отменён».

---

# 15. Корректировка платежа

Если была допущена ошибка (например, неверная сумма или квартира), запрещается изменять существующий платеж.

Правильный порядок действий:

1. Отменить ошибочный платеж.
2. Создать новый корректный платеж.
3. Повторно выполнить распределение.
4. Сохранить связь между отмененной и новой операцией для аудита.

---

# 16. Отмена расхода

Расход не удаляется.

При отмене:

1. Создается обратная расходная операция (сторно).
2. Баланс пересчитывается автоматически.
3. В истории остаются обе записи: исходная и сторнирующая.

---

# 17. Изменение владельца квартиры

Смена владельца не влияет на финансовую историю квартиры.

История начислений и оплат закреплена за квартирой, а не за пользователем.

Новый владелец получает доступ к полной истории квартиры в соответствии с установленными правилами доступа.

---

# 18. Работа с OCR и платежами

Если платеж создан автоматически на основании OCR-квитанции:

* сохраняется ссылка на исходный PDF;
* сохраняется распознанный текст;
* сохраняется уровень уверенности распознавания (confidence), если он поддерживается OCR;
* при необходимости администратор может выполнить ручную корректировку.

После корректировки выполняется повторное распределение платежа.

---

# 19. Работа с отрицательными сценариями

Система должна корректно обрабатывать следующие ситуации:

* попытка повторной оплаты по одной и той же банковской операции;
* загрузка одной и той же квитанции несколько раз;
* платеж с нулевой или отрицательной суммой;
* платеж на несуществующую квартиру;
* начисление за уже существующий период;
* отмена уже отмененной операции;
* распределение суммы, превышающей сумму платежа;
* ручное изменение распределений без прав администратора.

Все подобные действия должны завершаться понятной ошибкой без нарушения целостности данных.

---

# 20. Контроль целостности данных

Финансовое ядро должно обеспечивать следующие гарантии:

* сумма всех распределений по платежу не может превышать сумму платежа;
* сумма распределений по начислению не может превышать сумму начисления;
* у квартиры не может быть двух начислений за один месяц;
* каждая финансовая операция должна иметь источник;
* каждая операция должна иметь дату создания и автора (если действие выполнено пользователем);
* все изменения выполняются в рамках атомарных транзакций базы данных.

---

# 21. Финансовые инварианты системы

В любой момент должны выполняться следующие условия:

* **Получено** = сумма всех приходных транзакций.
* **Потрачено** = сумма всех расходных транзакций.
* **Баланс** = Получено − Потрачено.
* **Начислено по квартире** = сумма всех её начислений.
* **Оплачено по квартире** = сумма всех распределений по её начислениям.
* **Долг квартиры** = Начислено − Оплачено.
* **Общий долг дома** = сумма долгов всех квартир.

Если хотя бы один из этих инвариантов нарушен, система должна считать данные поврежденными и зафиксировать событие в журнале аудита.

---

# 22. Основной принцип финансового ядра

Все функции Backend и Frontend должны опираться на единый источник истины.

Источник истины:

1. **Начисления (`charges`)** — что должно быть оплачено.
2. **Платежи (`payments`)** — какие деньги поступили.
3. **Распределения (`payment_allocations`)** — какие начисления закрыты и в каком объеме.
4. **Финансовые операции (`transactions`)** — движение денежных средств.
5. **Расходы (`expenses`)** и **выплаты зарплаты (`salary_payments`)** — куда были израсходованы средства.

Никакие вычисляемые показатели (баланс, долг, переплата) не должны храниться как независимые данные. Они всегда рассчитываются на основании этих сущностей.

---

# 23. Критерии готовности финансового ядра

Финансовое ядро считается реализованным, если система в любой момент времени без ручных расчетов отвечает на следующие вопросы:

### Для жильца

* Сколько всего начислено?
* Сколько оплачено?
* Сколько осталось оплатить?
* За какие месяцы произведена оплата?
* Есть ли переплата?
* Когда был последний платеж?
* Какие чеки подтверждают мои оплаты?

### Для администратора

* Сколько денег поступило за любой период?
* Сколько начислено по дому?
* Какова задолженность по каждой квартире и по дому в целом?
* Сколько средств находится в кассе?
* Какие расходы произведены и кем утверждены?
* Сколько выплачено сотрудникам?
* Совпадает ли баланс с историей финансовых операций?
* Можно ли проследить происхождение каждой суммы от поступления до расходования?

Если на все эти вопросы система способна ответить автоматически, быстро и с полной прослеживаемостью данных, финансовое ядро считается реализованным в соответствии с данным техническим заданием.
